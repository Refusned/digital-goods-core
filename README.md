# Ядро магазина цифровых товаров

Тестовое задание «Бэкенд разработчик», **первый и второй этап в одном репозитории**.

Первый этап: заказы, вебхуки оплаты, автоматическая выдача кода с гарантией однократной выдачи
под гонками, устойчивые интеграции с двумя поставщиками, сверка и восстановление,
витрина остатков на тысячах SKU.

Второй этап (поверх первого, без переписывания):

* **заказ из нескольких товаров**, где часть позиций может не выдаться: выданное остаётся
  у покупателя, за невыданное возвращаются деньги, и по деньгам сходится при любом сбое и повторе;
* **поставщик, которому нельзя доверять**: дубль кода, чужой код, ответ «ошибка» при фактической
  выдаче. Расхождения находятся и разбираются автоматически, без человека;
* **всплеск заказов при лимите поставщика**: очередь с приоритетом, лимит не превышается,
  ничего не теряется, прогресс виден снаружи;
* **восстановление картины на любой момент**: append-only журнал событий, состояние заказа
  и баланс счетов на прошлую дату, итоги за период со сверкой двух независимых записей.

Стек: Node.js 20+ (ESM), Express, PostgreSQL 16. Из зависимостей только `express` и `pg`,
тесты на встроенном `node:test`.

## Запуск

```bash
docker compose up -d          # PostgreSQL на localhost:5442
cp .env.example .env
npm install
npm run migrate               # применяет только новые миграции, учёт в schema_migrations
npm run seed                  # каталог из задания + пул ключей, поделённый между поставщиками
npm start                     # API :3010, поставщики A :3121 и B :3122, платёжный шлюз :3131
```

Порты меняются в `.env`. Postgres можно взять и свой, достаточно поправить `DATABASE_URL`.

## Проверка

```bash
npm test                      # 57 тестов: оба этапа целиком
npm run race                  # 6 сценариев приёмки первого этапа против ЗАПУЩЕННОГО сервера
npm run stage2                # 18 сценариев приёмки второго этапа против ЗАПУЩЕННОГО сервера
npm run crash                 # аварийная остановка процесса посреди выдачи и восстановление
npm run bench:catalog         # витрина на 20 000 SKU: план запроса и время
```

Тесты второго этапа: `test/06-multi-item` (частичная выдача и возвраты), `test/07-untrusted-supplier`
(недобросовестный поставщик и автоматическая сверка), `test/08-surge` (лимит и очередь),
`test/09-history` (восстановление на дату).

`npm run crash` стоит особняком: он поднимает свой экземпляр сервиса на отдельных портах,
ставит поставщика в режим «код выдан, ответ не дойдёт», убивает процесс сигналом KILL ровно
в середине выдачи, поднимает сервис заново и проверяет, что заказ дошёл сам, выдач ровно две,
у поставщика израсходовано ровно два ключа и деньги сошлись. Это прямая проверка требования
«заказ доходит до конечного состояния даже после аварийной остановки и перезапуска».

`npm test` работает сразу после `docker compose up -d`: скрипт `scripts/test.js` создаёт отдельную
базу `<имя>_test`, накатывает туда миграции и только потом запускает сам прогон уже с этой базой.
Тестовые файлы дополнительно отказываются стартовать, если база не выглядит выделенной,
поэтому рабочие данные они стереть не могут. Своя база задаётся через `TEST_DATABASE_URL`.

⚠️ `npm run race` меняет данные: создаёт заказы и расходует ключи поставщиков. Поэтому он требует
явного подтверждения и запускается как `ALLOW_DESTRUCTIVE_RACE=1 npm run race` на демонстрационной базе.

### Как воспроизвести проверку гонок

50 параллельных вебхуков «оплачено» по одному заказу:

```bash
curl -s -XPOST localhost:3010/orders -H 'content-type: application/json' -d '{"sku":"KEY-CS2-PRIME"}'
node scripts/emit-webhook.js <order_id> --parallel 50
curl -s localhost:3010/orders/<order_id>
```

Ожидаемо: заказ `delivered`, ровно одна строка в `deliveries`, у поставщика израсходован один ключ.

Повторная доставка одного и того же события:

```bash
node scripts/emit-webhook.js <order_id> --parallel 20 --same-event
```

Один запрос применит платёж, остальные 19 вернут `outcome: "duplicate"`. Повторный запуск
той же команды с уже использованным `--event-id evt_...` даст `duplicate` на всех 20.

### Как воспроизвести отказ и фолбэк поставщика

Заглушки принимают сценарий поведения на следующие вызовы:

```bash
# A выдаёт код и зависает: ответ не дойдёт (ловушка таймаута)
curl -XPOST localhost:3121/_chaos -H 'content-type: application/json' \
     -d '{"script":["timeout_issue"],"hangMs":3000}'

# A отвечает явным отказом три раза подряд -> заказ уходит на резервного B
curl -XPOST localhost:3121/_chaos -H 'content-type: application/json' -d '{"script":["error","error","error"]}'

# случайные сбои: 30% ошибок и 20% таймаутов
curl -XPOST localhost:3121/_chaos -H 'content-type: application/json' -d '{"errorRate":0.3,"timeoutRate":0.2}'

curl localhost:3121/_stats        # сколько ключей осталось и сколько выдано
```

## API

| Метод | Путь | Назначение |
|---|---|---|
| `POST` | `/orders` | создать заказ по SKU. Тело: `{ "sku", "order_id"?, "buyer_contact"? }`, заголовок `Idempotency-Key` опционален |
| `GET` | `/orders/:id` | заказ со статусом и выданным кодом |
| `POST` | `/webhook/payment` | вебхук платёжной системы по контракту из задания |
| `GET` | `/catalog?type=&limit=` | витрина остатков |
| `GET` | `/catalog/:sku` | карточка товара |
| `GET` | `/admin/reconciliation?overdue_seconds=` | отчёт сверки, операционное здоровье и баланс журнала денег |
| `POST` | `/admin/orders/:id/deliver` | безопасная ручная доводка заказа (идемпотентна) |
| `POST` | `/admin/stock/:sku/restock` | завезти ключи поставщику и пересчитать витрину |
| `GET` | `/health` | проверка живости |

`order_id` в `POST /orders` необязателен: он нужен, когда платёжная система узнаёт идентификатор
заказа раньше нас и может прислать вебхук до того, как заказ будет создан.

## Статусы заказа

`created → paid → delivering → delivered`

Ветки: `created → payment_failed`; `paid → delivering → out_of_stock → delivered` (после завоза);
`paid → delivering → delivery_failed → delivered` (после повторной выдачи).
`out_of_stock` и `delivery_failed` восстановимые: заказ забирает фоновый воркер, повторы идемпотентны.


## Второй этап

### Заказ из нескольких товаров и частичный возврат

Каждая единица товара это отдельная **позиция** (`order_items`) со своей судьбой: своим поставщиком,
своим кодом, своим сроком ожидания. Заказ из одного товара это заказ из одной позиции, поэтому
контракт первого этапа не изменился, а `POST /orders` принимает оба формата:

```bash
# первый этап, как было
curl -s -XPOST localhost:3010/orders -H 'content-type: application/json' \
     -d '{"sku":"KEY-CS2-PRIME"}'

# второй этап: несколько товаров, у каждой единицы свой код
curl -s -XPOST localhost:3010/orders -H 'content-type: application/json' \
     -d '{"items":[{"sku":"KEY-CS2-PRIME","qty":2},{"sku":"KEY-GTA5"}]}'
```

Итоговые состояния заказа: `delivered` (выдано всё), `partially_delivered` (часть выдана,
за остальное вернули деньги), `refunded` (не выдано ничего, вернули всё).

Позиция, которую не удалось выдать за отведённый срок (`DELIVERY_DEADLINE_MS`) или за отведённое
число попыток, объявляется невыдаваемой, и за неё начисляется возврат. Срок нужен именно для того,
чтобы заказ ГАРАНТИРОВАННО доходил до конечного состояния: бесконечное ожидание кода это тоже
способ потерять деньги покупателя. «Нет остатка» при этом счётчик попыток не тратит: это ожидание
завоза, а не отказ системы, и его ограничивает только срок.

**Как воспроизвести частичный сбой заказа**

```bash
# 1. заказ из двух товаров, ключей на второй нет ни у одного поставщика
ORDER=$(curl -s -XPOST localhost:3010/orders -H 'content-type: application/json' \
        -d '{"items":[{"sku":"KEY-CS2-PRIME"},{"sku":"SUB-DISCORD-1M"}]}' \
        | python3 -c 'import sys,json;print(json.load(sys.stdin)["id"])')

# 2. оплата
curl -s -XPOST localhost:3010/webhook/payment -H 'content-type: application/json' \
     -d "{\"event_id\":\"evt_1\",\"order_id\":\"$ORDER\",\"status\":\"paid\",\"amount\":<сумма>,\"currency\":\"RUB\",\"created_at\":\"2026-01-01T12:00:00Z\"}"

# 3. заказ: одна позиция delivered, вторая refunded, статус partially_delivered
curl -s localhost:3010/orders/$ORDER
```

То же самое одной командой и с проверками: `ALLOW_DESTRUCTIVE_RACE=1 npm run stage2`.

### Деньги: как проверить, что сходится

Инвариант второго этапа: **оплачено = выдано + возвращено + ещё в работе**, и последнее
слагаемое никогда не отрицательно. Он держится не аккуратностью кода, а журналом двойной записи:

| Событие | Проводка |
|---|---|
| оплата | `cash` ← `deferred_revenue` |
| выдача позиции | `deferred_revenue` → `revenue` |
| решение о возврате | `deferred_revenue` → `refunds_payable` |
| выплата возврата | `refunds_payable` → `cash` |

Каждая проводка уникальна по `txn_id` (`pay:<order>`, `deliver:<item>`, `refund_accrue:<item>`,
`refund_settle:<item>`), поэтому повтор любого шага не может задвоить деньги.

```bash
curl -s localhost:3010/orders/$ORDER | python3 -m json.tool          # блок money по заказу
curl -s localhost:3010/admin/reconciliation                          # ledger.balanced и money_per_order_broken
```

`money_per_order_broken` это список заказов, где инвариант нарушен. Пустой список и есть ответ
на вопрос «деньги сходятся».

### Поставщик, которому нельзя доверять

Ответу поставщика не верят на слово нигде:

| Поведение поставщика | Что делает ядро |
|---|---|
| прислал код, уже принадлежащий другой выдаче | уникальный индекс `deliveries.code` не даёт записать; код возвращается поставщику (`POST /release`), у него запрашивается замена НОВЫМ `request_id` |
| прислал код от другого товара | принадлежность кода проверяется через `GET /verify?code=`; чужой код отбраковывается и возвращается |
| ответил ошибкой, хотя код выдал | перед признанием отказа ядро спрашивает `GET /issued/:request_id`; если код выдан, забирается он, а не запрашивается второй |
| молчит (таймаут) | исход неизвестен: резервный поставщик запрещён, повтор идёт с тем же `request_id` |
| соединение не установилось | единственный доказанный отказ: байты не ушли, разрешён резервный поставщик |

Замена негодного кода просится новым запросом следующей **эпохи** (`req_<item>_<supplier>_e1`):
внутри эпохи `request_id` неизменен, поэтому защита от ловушки таймаута продолжает работать,
а «дай другой код» становится осознанным отдельным действием.

Поверх этого раз в `SUPPLIER_RECONCILER_INTERVAL_MS` идёт **независимая сверка** журнала выдач
поставщика (`GET /journal?after=`) со своими выдачами. Она чинит то, о чём поставщик молчит:

* `lost_code` — поставщик считает код выданным нам, а у нас выдачи нет (процесс умер между
  ответом и записью): код подбирается и доводится до покупателя;
* `orphan_issue` — за нами числится код, который не нужен: возвращается на склад;
* `silent_issue`, `duplicate_code`, `foreign_code` — фиксируются как инциденты с разбором.

```bash
curl -s localhost:3010/admin/discrepancies   # что нашли и как разобрали
curl -s -XPOST localhost:3010/admin/audit/run   # ручной прогон той же сверки
```

**Как воспроизвести недобросовестное поведение**

```bash
curl -XPOST localhost:3121/_chaos -H 'content-type: application/json' -d '{"script":["duplicate_code"]}'
curl -XPOST localhost:3121/_chaos -H 'content-type: application/json' -d '{"script":["foreign_code"]}'
curl -XPOST localhost:3121/_chaos -H 'content-type: application/json' -d '{"script":["error_after_issue"]}'
```

### Всплеск заказов и лимит поставщика

Лимит известен по договору, поэтому задача не «обработать 429», а не отправить лишний запрос.
Разрешения выдаёт счётчик **скользящего окна** в БД: считаем ровно так же, как считает поставщик.
Ведро токенов здесь не подошло бы: накопленный за простой запас плюс текущее пополнение дают
в одном окне больше договорного лимита. Собственное окно берётся на 15% шире договорного,
потому что поставщик отмечает момент приёма запроса, а мы момент выдачи разрешения.

Очередь это позиции, отсортированные по `(priority, queued_at)`. Приоритет 0 у оплаченных,
100 у резерва до оплаты (`POST /orders {"reserve": true}`), поэтому деньги покупателя всегда
обслуживаются раньше. Позиция, которой не хватило лимита, возвращается в очередь немедленно
и без штрафной задержки: она ни в чём не виновата, а отсрочка отправила бы её в хвост.

```bash
curl -XPOST localhost:3121/_chaos -H 'content-type: application/json' \
     -d '{"rateLimitPerMin":30,"rateLimitWindowMs":1000}'      # поставщик: 30 выдач в секунду
curl -XPOST localhost:3010/admin/suppliers/A/rate-limit -H 'content-type: application/json' \
     -d '{"capacity":30,"window_ms":1000}'                     # наш лимит по договору

curl -s localhost:3010/admin/queue      # queued, in_flight, delivered, oldest_wait_ms, rate_limits
curl -s localhost:3121/_stats           # calls.rate_limited должен остаться нулём
```

### Восстановление картины на любой момент

`order_events` и `ledger_entries` только дополняются: правку и удаление запрещает триггер в БД,
а не договорённость в коде.

```bash
curl -s "localhost:3010/orders/$ORDER/at?ts=2026-09-08T08:00:00Z"    # состояние заказа на момент
curl -s "localhost:3010/admin/ledger/at?ts=2026-09-08T08:00:00Z"     # баланс счетов на момент
curl -s "localhost:3010/admin/report?from=...&to=..."                # итоги за период
```

Состояние заказа собирается сворачиванием событий, а не чтением текущих строк: смысл ручки
в том, чтобы показать прошлое, а не пересказать настоящее. Отчёт за период считает одно и то же
двумя независимыми путями (журнал событий и журнал денег) и выкладывает расхождение
в `cross_check`: там должны быть нули.

## Как закрыты критерии приёмки

| Критерий | Где проверяется |
|---|---|
| 50 параллельных вебхуков → одна выдача, без потерь | `test/02-exactly-once.test.js`, `npm run race` |
| Повторный вебхук с тем же `event_id` ничего не меняет | `test/02`, `emit-webhook.js --same-event` |
| Вебхук вне порядка или раньше заказа | `test/02`: раннее событие, обе перестановки `paid`/`failed`, одинаковые timestamp |
| Таймаут поставщика, который выдал код → нет второй выдачи | `test/03-suppliers.test.js`: таймаут, обрыв сокета после выдачи, 50 параллельных повторов одного `request_id` |

| Деньги: оплата без суммы или в чужой валюте не выдаёт товар | `test/01-core.test.js`, `npm run race` |
